# MotoLog — 바이크 통합 관리 프로젝트 프롬프트 초안

## 1. 공통 지시문

지금부터 바이크 정보, 라이딩 로그, 정비 기록을 한곳에서 관리하는 웹페이지를 단계별로 만들 것이다.

프로젝트 이름은 임시로 **MotoLog**로 한다. 

### 기술과 배포

- 순수 HTML, CSS, JavaScript를 사용한다.
- Supabase JavaScript SDK v2를 사용한다.
- 데이터는 Supabase PostgreSQL에 저장한다.
- 회원 관리는 Supabase Auth, 사진은 Supabase Storage를 사용한다.
- GitHub Pages에서 배포할 수 있게 상대 경로로 구성한다.
- React, Node.js 서버, 빌드 도구는 사용하지 않는다.
- 첫 버전에서는 IndexedDB와 오프라인 동기화를 구현하지 않는다.
- 코드는 역할별로 나누되, 입문자가 이해하기 어려울 정도로 복잡하게 분리하지 않는다.

### 서비스 방향

- 로그인한 사용자가 자신의 바이크와 관련 기록을 관리하는 개인용 서비스다.
- 상단 탭으로 `대시보드 / 내 바이크 / 라이딩 로그 / 정비 기록`을 구분한다.
- 대시보드에서 각 탭의 핵심 정보를 통합해서 보여준다.
- PC와 모바일에서 모두 사용 가능한 한국어 반응형 화면으로 만든다.
- 첫 버전은 바이크 1대 관리 흐름에 집중하되, 기록은 바이크 ID와 연결한다.

### 작업 규칙

- 내가 요청한 단계만 진행하고, 다음 단계 기능을 임의로 추가하지 않는다.
- 미정 사항은 권장안을 제시하되 확정된 요구사항과 구분한다.
- DB 구성 SQL은 별도 파일로 작성하며, Supabase에서의 실행은 내가 직접 한다.
- 기존 파일과 데이터를 임의로 삭제하지 않는다.
- DB 변경이 필요하면 초기 설치 SQL과 기존 DB 수정 SQL을 구분한다.
- 실제 Supabase 연결이 실패했을 때 임시 배열이나 로컬 저장으로 조용히 대체하지 않는다.
- 완료 후 변경 파일, 확인 방법, 내가 직접 설정해야 할 사항을 간단히 설명한다.
- GitHub 커밋·푸시·배포는 별도 요청을 받았을 때 진행한다.

## 2. 화면과 주요 기능

### 대시보드

- 바이크 사진, 모델명, 현재 계기판 주행거리를 표시한다.
- 이번 달 라이딩 횟수, 기록된 주행거리 합계, 정비 비용 합계를 표시한다.
- 최근 라이딩과 최근 정비 기록을 요약해서 보여준다.
- 사용자가 지정한 다음 점검 날짜·주행거리 기준을 보여준다.
- 라이딩 추가, 정비 추가 버튼을 제공한다.
- 요약 항목에서 관련 탭이나 상세 기록으로 이동할 수 있게 한다.
- 데이터가 없으면 등록을 안내하는 빈 화면을 제공한다.

### 내 바이크

- 바이크 정보를 등록·조회·수정한다.
- 후보 필드: 이름 또는 별명, 제조사, 모델, 연식, 구매일, 현재 계기판 주행거리, 사진, 메모.
- 처음 등록한 사용자는 바이크 등록부터 안내한다.
- 계기판 주행거리와 앱에 기록된 라이딩 거리 합계를 구분한다.
- 초기에는 현재 계기판 주행거리를 직접 입력하며, 로그 등록만으로 자동 덮어쓰지 않는다.

### 라이딩 로그

- 라이딩 기록을 등록·조회·수정·삭제한다.
- 후보 필드: 제목, 날짜, 출발지, 경유지, 도착지, 주행거리, 출발·도착 시간, 유형, 메모.
- 경유지는 여러 개 추가하고 순서를 변경할 수 있게 한다.
- 최신순 목록과 상세 화면을 제공한다.
- 제목·장소 검색 및 기간·유형 필터를 제공한다.
- 첫 버전의 경로는 장소를 직접 입력한 방문 순서다. 실제 도로 궤적으로 표현하지 않는다.
- 지도, GPS 실시간 추적, GPX 가져오기는 확장 기능으로 남긴다.

### 정비 기록

- 정비 기록을 등록·조회·수정·삭제한다.
- 후보 필드: 정비일, 항목, 당시 계기판 주행거리, 비용, 정비소 또는 자가 정비 여부, 메모.
- 정비 항목 예시: 엔진오일, 오일필터, 체인, 타이어, 브레이크, 배터리, 기타.
- 다음 점검 날짜와 다음 점검 계기판 주행거리를 선택적으로 입력한다.
- 최신순 목록 및 항목·기간 필터를 제공한다.
- 점검 표시는 사용자 설정값에 근거하며 제조사 권장 주기를 임의로 단정하지 않는다.
- 알림은 우선 화면 안에서만 표시한다. 이메일·푸시 알림은 제외한다.

### 로그인과 계정

- 이메일·비밀번호 회원가입, 로그인, 로그아웃을 제공한다.
- 새로고침 후 로그인 상태를 복원한다.
- 이메일 확인 설정에 따라 가입 후 안내를 다르게 표시한다.
- 로그아웃하거나 계정이 바뀌면 이전 사용자의 데이터를 즉시 비운다.
- 이전 계정의 진행 중 요청이 늦게 완료되어 새 계정 화면에 표시되지 않도록 한다.

## 3. 데이터 구조 방향

세부 컬럼과 타입은 DB 설계 단계에서 제안한다. 아래는 관계의 개괄이다.

| 구분 | 역할 | 관계 |
| --- | --- | --- |
| Supabase Auth 사용자 | 계정과 인증 | 사용자가 바이크를 소유 |
| bikes | 바이크 기본 정보 | 사용자와 연결 |
| riding_logs | 라이딩 기록 | 사용자 및 바이크와 연결 |
| maintenance_logs | 정비 기록 | 사용자 및 바이크와 연결 |
| 사진 정보 | Storage 파일의 경로와 연결 정보 | 사진 기능 단계에서 확정 |

- 각 기록에 기본키와 생성·수정 시각을 둔다.
- 거리·금액 등 숫자에 유효성 제약을 둔다.
- 라이딩·정비 기록을 다른 사용자의 바이크에 연결할 수 없도록 DB에서도 제한한다.
- 사용자별 접근과 관련 레코드의 소유권 검증을 RLS·제약조건에 반영한다.
- 바이크 삭제 시, 바이크 정보에 삭제된 바이크라는 상태값을 반영하고 기존 데이터에도 이를 반영한다.
- 사진 원본은 DB에 직접 저장하지 않고 Storage에 저장한다.
- 샘플은 가상 데이터로 분리하고 실제 사용자의 기록과 섞지 않는다.

## 4. 권한과 공통 품질 기준

- 비밀번호를 저장하는 자체 회원 테이블을 만들지 않는다.
- 브라우저 코드에는 Project URL과 Publishable key만 사용한다.
- Secret key와 service_role 키를 웹 코드나 GitHub에 넣지 않는다.
- 사용자 데이터 테이블에 RLS를 활성화하고 본인 데이터만 CRUD 가능하도록 한다.
- 화면에서 숨기는 것만으로 권한 처리를 끝내지 않는다.
- 오류 해결을 위해 RLS를 끄거나 전체 공개 권한을 부여하지 않는다.
- 사진에도 소유자 기준 Storage 접근 정책을 적용한다.
- DB 문자열과 사용자 입력은 textContent 등 안전한 방식으로 표시한다.
- 모든 Supabase 요청의 오류를 확인한다.
- 로딩, 데이터 없음, 저장 중, 성공, 실패 상태를 구분한다.
- 중복 제출을 막고, 실패한 저장을 성공으로 표시하지 않는다.
- 삭제 전 확인하고 입력 오류는 해당 필드 근처에 표시한다.
- 날짜는 한국 기준으로 표시하고, 거리 km·금액 원 등 단위를 명시한다.
- 필수 입력, 음수 거리·금액, 시간 범위 등 기본 검증을 적용한다.
- 탭·버튼·입력란은 키보드로도 사용할 수 있게 한다.

## 5. 디자인 방향

- 개인 차고와 주행 기록을 관리하는 깔끔한 대시보드 느낌으로 만든다.
- 바이크 사진, 요약 카드, 최근 기록 목록을 중심으로 구성한다.
- 장식보다 기록 입력과 조회가 편한 화면을 우선한다.
- 모바일에서는 카드와 입력 폼이 한 열로 배치되도록 한다.
- 임시 샘플 모델로 Honda GB350을 사용할 수 있지만 모델명이나 통계값을 실제 화면에 하드코딩하지 않는다.
- 색상·폰트·밝은 테마 또는 어두운 테마는 디자인 단계에서 결정한다.

## 6. 첫 버전과 확장 범위

### 첫 버전

- 회원가입·로그인·로그아웃
- 바이크 기본 정보 관리
- 라이딩 로그 CRUD 및 기본 검색·필터
- 정비 기록 CRUD 및 기본 검색·필터
- 실제 저장된 기록을 집계한 대시보드
- PC·모바일 반응형 화면

### 기본 기능 완료 후 추가

- 바이크 대표 사진 및 기록별 사진 첨부
- 다음 점검 기준 표시
- 여러 바이크 등록 및 선택
- 통계 차트와 달력
- 데이터 내보내기·가져오기
- 지도 및 GPX 파일 기반 주행 궤적

## 7. 단계별로 전달할 요청

아래 요청은 한 번에 모두 실행하지 않고, 이전 단계 결과를 확인한 뒤 하나씩 전달한다.

### 1단계 — 요구사항과 화면 구조 정리

위 요구사항을 읽고 프로젝트 범위, 탭별 화면 구성, 데이터 관계, 구현 순서를 간단히 정리해 줘. 미정 사항은 별도로 표시해 줘. 지금은 코드나 SQL을 만들지 마.

### 2단계 — DB 설계와 SQL

확정한 요구사항에 맞춰 간단한 ERD와 테이블·컬럼 정의를 작성해 줘. 새 프로젝트용 database.sql에 테이블, 관계, 검증 제약, 인덱스, 최소 권한과 RLS 정책을 포함해 줘. 다른 사용자의 바이크에 기록을 연결할 수 없도록 해 줘. SQL 재실행 시 동작과 내가 직접 실행할 순서를 설명해 줘. 아직 웹 화면은 만들지 마.

### 3단계 — 기본 화면

확정한 화면 구조에 맞춰 HTML·CSS·JavaScript 기본 화면을 만들어 줘. 대시보드, 내 바이크, 라이딩 로그, 정비 기록 탭과 반응형 레이아웃을 구성해 줘. 이 단계의 예시 데이터는 UI 시연용임을 명확히 표시해 줘. Supabase 연결 단계에서는 실제 데이터로 교체할 수 있게 구성해 줘.

### 4단계 — 인증과 바이크 정보 연결

Supabase 설정 파일과 인증을 연결하고 내 바이크 등록·조회·수정을 구현해 줘. 설정값에는 자리표시자를 사용하고 내가 URL·공개 키를 넣을 위치를 알려줘. 로그인 상태 복원, 이메일 확인 안내, 로그아웃 시 화면 초기화를 처리해 줘. Supabase에서 직접 설정할 항목도 안내해 줘.

### 5단계 — 라이딩·정비 기록 연결

기존 SQL과 코드를 읽고 라이딩 로그와 정비 기록의 CRUD, 검색·필터를 구현해 줘. 입력 검증과 요청 상태를 처리하고 실제 DB 저장 결과를 화면에 반영해 줘. 본인 기록 접근 및 다른 사용자 기록 접근 차단을 확인하는 방법을 안내해 줘.

### 6단계 — 대시보드와 마무리

실제 저장된 데이터로 요약 수치와 최근 기록을 표시해 줘. 계기판 주행거리와 라이딩 거리 합계를 구분해 줘. 모바일 화면, 빈 데이터, 오류, 계정 전환, CRUD 및 권한을 점검해 줘. README에 실행·설정·GitHub Pages 배포 방법과 알려진 제한을 정리해 줘. 실제 푸시와 배포는 하지 마.

### 선택 단계 — 사진과 점검 표시

기본 기능이 정상 동작한 상태에서 사진 저장과 다음 점검 표시를 추가해 줘. 사진의 확장자·용량 제한, 소유자 접근 정책, 교체·삭제 시 파일 처리 방식을 정리해 줘. 점검 표시는 사용자가 입력한 날짜·계기판 주행거리 기준으로 계산해 줘.
