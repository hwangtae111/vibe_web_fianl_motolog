# MotoLog — Codex 전달용 최종 요구사항 및 테이블 설계

> 사용자와 합의한 요구사항을 정리한 구현 기준 문서. 아래의 명시적 미정 항목만 추후 확정한다.
> SQL이나 앱을 이미 구현했다는 의미는 아니다. Codex는 이 문서를 기준으로 단계별 작업을 진행한다.
> 대상: 순수 HTML/CSS/JavaScript + Supabase + GitHub Pages.
> 첫 화면은 바이크 1대 중심으로 구성하되, DB는 여러 대를 지원할 수 있게 설계한다.

## 0. Codex 작업 지침과 화면 범위

- 순수 HTML/CSS/JavaScript와 Supabase JavaScript SDK v2를 사용한다. React, 빌드 도구, 별도 Node.js 서버는 사용하지 않는다.
- GitHub Pages에서 상대 경로로 실행되게 한다. IndexedDB 동기화는 범위에서 제외한다.
- 한국어·밝은 대시보드·반응형 화면으로 구성한다.
- 탭은 `대시보드 / 내 바이크 / 라이딩 로그 / 정비 기록`으로 구분한다.
- 바이크·라이딩·정비 등록과 수정, 라이딩·정비 삭제, 검색·기간 필터, 요약 집계를 제공한다. 바이크·계정 삭제 요청은 아래 아카이브 규칙을 따른다.
- 첫 화면은 바이크 1대 기준으로 만들고, 첫 화면 생성 후 여러 바이크 선택 UI를 추가한다. DB에는 사용자당 1대 제한을 두지 않는다.
- 바이크 사진 1장은 선택 기능으로 제출 버전에 포함하되 기본 CRUD 이후 연결한다. 라이딩·정비 사진, 지도·GPS·GPX는 현재 범위에서 제외한다.
- 회원가입·이메일/비밀번호 로그인·로그아웃·로그인 상태 복원을 제공한다. 이메일 확인 필요 여부에 따라 안내한다.
- 로딩·빈 결과·오류·저장 중·성공 상태를 구분하고 요청 중 중복 제출을 막는다.
- 로그아웃·계정 전환 시 이전 데이터를 비우고 이전 요청 응답이 새 계정에 표시되지 않게 한다.
- 사용자 문자열은 textContent 등 안전한 방법으로 표시하고 Supabase 응답의 error를 확인한다.
- 설정 파일에는 URL·Publishable key 자리표시자만 제공한다. Secret/service_role 키를 웹 코드나 GitHub에 넣지 않는다.
- SQL은 파일로 작성하고 내가 Supabase에서 직접 실행한다. 기존 파일·데이터를 임의 삭제하지 않는다.
- 미정 사항을 임의 확정하지 않는다. 유형 이름이 없어도 코드로 표시해 진행할 수 있다.
- 요청한 단계만 구현하고, 완료 후 변경 파일·검증 결과·수동 설정 사항을 설명한다. 푸시·배포는 별도 요청 시 진행한다.

## 1. 전체 구조

직접 만드는 서비스 테이블은 3개다.

| 테이블 | 역할 | 관계 |
| --- | --- | --- |
| `public.bikes` | 바이크 기본 정보 | 사용자 1명 → 바이크 여러 대 |
| `public.riding_logs` | 라이딩 기록 | 바이크 1대 → 라이딩 기록 여러 개 |
| `public.maintenance_logs` | 정비 기록 | 바이크 1대 → 정비 기록 여러 개 |

- 사용자 계정은 Supabase Auth의 `auth.users`를 사용한다.
- 바이크 대표 사진은 Storage에 저장하고, `bikes`에는 파일 경로만 저장한다.
- 대시보드는 위 데이터를 조회·집계해 표시한다. 별도 대시보드 테이블은 만들지 않는다.
- 경유지는 `riding_logs`의 JSON 배열로 저장한다. 첫 버전에는 별도 경유지 테이블을 만들지 않는다.

## 2. 공통 표기와 타입

| 표기·타입 | 의미 |
| --- | --- |
| 필수 | DB에서 `NOT NULL`로 제한 |
| 선택 | 입력하지 않으면 `NULL` 허용 |
| `uuid` | 사용자·바이크·기록을 식별하는 ID |
| `text` | 문자열. 필요한 길이·공백 검증은 별도 적용 |
| `integer` | 소수점 없는 정수. 연식·원 단위 금액 등에 사용 |
| 거리용 `integer` | km 단위 정수. 소수점 입력은 허용하지 않음 |
| `date` | 시각 없는 날짜. 구매일·정비일 등에 사용 |
| `timestamptz` | 시간대 정보를 바탕으로 같은 시점을 저장하는 날짜·시각 |
| `jsonb` | 경유지처럼 구조가 있는 JSON 데이터 |

- 거리 단위는 km, 비용 단위는 원(KRW)으로 통일한다. 거리·금액 모두 정수로 입력한다. 소수를 자동 반올림하지 않고 입력 오류로 처리한다.
- 날짜·시각은 화면에서 한국 시간으로 표시한다.
- 선택 숫자에서 `NULL`은 미입력, `0`은 실제 0이다. 둘을 구분한다.

## 3. bikes — 바이크 정보

| 컬럼 | 타입 | 필수 여부 | 기본값·제약 기준 | 설명·예시 |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | 필수 | PK, `gen_random_uuid()` | 바이크 고유 ID |
| `user_id` | `uuid` | 필수 | FK → `auth.users.id`, 기본값 `auth.uid()` | 소유 사용자 |
| `nickname` | `text` | 선택 | 최대 50자, 빈 문자열은 NULL | 별명: 검둥이 |
| `manufacturer` | `text` | 필수 | 1~50자, 자유 입력 | Honda |
| `model` | `text` | 필수 | 1~50자, 자유 입력 | GB350 |
| `model_year` | `integer` | 선택 | 4자리 양의 정수(1000~9999) | 모델 연식: 2026 |
| `purchase_date` | `date` | 선택 | 오늘 이하 | 2026-05-10 |
| `current_odometer_km` | `integer` | 필수 | 0 이상, 자동 기본값 없음 | 현재 확인한 계기판 누적거리: 1250 |
| `odometer_recorded_at` | `timestamptz` | 필수 | 최초 `now()`, 계기판 값 갱신 시 갱신 | 계기판 값을 확인·입력한 시점 |
| `status` | `text` | 필수 | 기본값 `active`, 허용값 `active` / `archived` | 사용 중 / 보관 |
| `photo_path` | `text` | 선택 | Storage 내부 경로 | 사용자ID/바이크ID/파일명.jpg |
| `notes` | `text` | 선택 | 최대 2,000자 | 차량 특징·메모 |
| `created_at` | `timestamptz` | 필수 | `now()` | 최초 등록 시각 |
| `updated_at` | `timestamptz` | 필수 | `now()` + 수정 트리거 | 마지막 수정 시각 |

### 주의사항

- `user_id`에 사용자당 1대라는 UNIQUE 제한을 두지 않는다. 화면 흐름만 1대 중심으로 시작한다.
- 현재 계기판 값은 사용자가 직접 입력한다. 중고 바이크의 누적거리를 0으로 자동 처리하지 않는다.
- 앱에 저장된 라이딩 거리 합계와 계기판 누적거리는 서로 다른 값이다.
- 과거 로그 등록·수정만으로 현재 계기판 값을 자동 변경하지 않는다.
- `updated_at`은 사진·메모 수정에도 바뀌므로 계기판 확인 시점으로 사용하지 않는다.
- 바이크 사진은 선택 입력이다. 사진 없이 등록할 수 있고 기본 이미지를 표시한다.
- 제조사·모델은 자유 입력이며, 구매일·연식은 선택 입력이다.
- 서명 URL처럼 만료되는 주소 대신 Storage 경로를 저장하고 표시 시 접근 URL을 구한다.
- 모든 바이크 삭제 요청은 연결 로그 유무와 관계없이 실제 삭제 대신 `status = archived`로 변경한다. 기록·사진은 보존하고 별도 보관 목록에서 조회·복원한다.
- 기본 목록과 대시보드는 `active` 바이크만 표시한다. 연결 로그가 없어도 실제 삭제하지 않는다.

## 4. riding_logs — 라이딩 로그

| 컬럼 | 타입 | 필수 여부 | 기본값·제약 기준 | 설명·예시 |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | 필수 | PK, `gen_random_uuid()` | 라이딩 고유 ID |
| `user_id` | `uuid` | 필수 | FK → `auth.users.id`, 기본값 `auth.uid()` | 기록 소유 사용자 |
| `bike_id` | `uuid` | 필수 | 본인 바이크 참조 | 라이딩에 사용한 바이크 |
| `title` | `text` | 필수 | 1~100자 | 양평 주말 라이딩 |
| `ride_date` | `date` | 필수 | 오늘 이하 | 출발한 한국 현지 날짜 |
| `start_location` | `text` | 필수 | 1~100자 | 중곡동 |
| `waypoints` | `jsonb` | 필수 | 기본값 `'[]'::jsonb`, 각 장소명 1~100자 | `["팔당", "양평"]` |
| `end_location` | `text` | 필수 | 1~100자 | 중곡동 |
| `distance_km` | `integer` | 필수 | 0 초과 | 해당 라이딩 거리: 128 |
| `started_at` | `timestamptz` | 선택 | 종료 시각과 함께 입력 권장 | 실제 출발 날짜·시각 |
| `ended_at` | `timestamptz` | 선택 | 출발 시각 이후 | 실제 도착 날짜·시각 |
| `ride_type` | `text` | 필수 | R + 양의 정수 형식, 기본값 없음 | 한국어 표시명은 이후 확정 |
| `notes` | `text` | 선택 | 최대 2,000자 | 소감·방문 장소 메모 |
| `created_at` | `timestamptz` | 필수 | `now()` | 최초 등록 시각 |
| `updated_at` | `timestamptz` | 필수 | `now()` + 수정 트리거 | 마지막 수정 시각 |

### 주의사항

- 경유지 배열의 순서가 방문 순서다. 화면에서 순서를 바꾸면 전체 배열을 갱신한다.
- 첫 버전은 장소 이름만 저장한다. 위도·경도, 도로 궤적, 지도 경로를 의미하지 않는다.
- 배열 여부뿐 아니라 각 원소가 비어 있지 않은 문자열인지 검증한다. 중복 장소는 재방문일 수 있어 허용한다.
- 실제 GPS 기록이 없으면 소요 시간을 실제 주행 시간으로 부르지 않는다. 도착−출발은 휴식 포함 경과 시간이다.
- 자정을 넘는 라이딩을 위해 시각만 저장하는 `time` 대신 날짜를 포함한 `timestamptz`를 사용한다.
- 출발·도착 시각은 둘 다 입력하거나 둘 다 비우는 것을 권장한다. 둘 다 있으면 `ended_at > started_at`을 DB에서도 확인한다.
- `ride_date`는 시각을 모르는 기록도 입력하기 위해 둔다. 출발 시각이 있으면 한국 기준 날짜와 일치하도록 검증한다.
- 소요 시간은 출발·도착 시각으로 계산하고 별도 컬럼에 중복 저장하지 않는다.
- 라이딩 유형은 `R1`, `R2`, `R3` 등의 코드로 저장한다. 코드별 한국어 이름과 전체 허용 목록은 이후 확정하며 임의로 의미를 부여하지 않는다. 확정 전에는 `^R[1-9][0-9]*$` 형식만 검증하고 코드 자체를 표시한다.
- 사진은 초기 라이딩 테이블에 포함하지 않는다. 여러 장 첨부는 이후 별도 사진 테이블을 검토한다.

## 5. maintenance_logs — 정비 기록

| 컬럼 | 타입 | 필수 여부 | 기본값·제약 기준 | 설명·예시 |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | 필수 | PK, `gen_random_uuid()` | 정비 기록 고유 ID |
| `user_id` | `uuid` | 필수 | FK → `auth.users.id`, 기본값 `auth.uid()` | 기록 소유 사용자 |
| `bike_id` | `uuid` | 필수 | 본인 바이크 참조 | 정비한 바이크 |
| `maintenance_date` | `date` | 필수 | 오늘 이하 | 실제 정비한 날짜 |
| `items` | `jsonb` | 필수 | 비어 있지 않은 정비 항목 배열, 각 항목 검증 | 아래 구조 예시 참고 |
| `title` | `text` | 필수 | 1~100자 | 엔진오일 교체 |
| `odometer_km` | `integer` | 선택 | 0 이상 | 정비 당시 계기판 값. 모르면 NULL |
| `cost_krw` | `integer` | 필수 | 항목별 비용 합계를 DB에서 계산·검증 | 해당 방문 총비용. 0 허용 |
| `service_type` | `text` | 필수 | 기본값 `unknown`, 허용값 CHECK | shop / self / unknown |
| `shop_name` | `text` | 선택 | 최대 100자, 빈 문자열은 NULL | 정비소 이름 |
| `next_due_date` | `date` | 필수 | 정비일 + 달력 기준 6개월, DB에서 계산 | 정비일 수정 시 함께 재계산 |
| `notes` | `text` | 선택 | 최대 2,000자 | 오일 제품명·작업 내용 등 |
| `created_at` | `timestamptz` | 필수 | `now()` | 최초 등록 시각 |
| `updated_at` | `timestamptz` | 필수 | `now()` + 수정 트리거 | 마지막 수정 시각 |

### 주의사항

- 한 행은 한 번의 정비 방문·자가 정비 작업을 의미한다. 그 안에 여러 정비 항목을 입력한다.
- 서비스 테이블 3개를 유지하도록 `items` JSON 배열을 사용한다. 항목별 상세 검색·통계가 중요해지면 별도 `maintenance_items` 테이블로 분리하는 방안을 검토한다.
- 각 항목은 정비 코드 `type_code`, 작업명 `name`, 비용 `cost_krw`, 선택 메모 `notes`를 가진다.
- 정비 코드는 `F1`, `F2`, `F3` 등으로 저장한다. 한국어 이름과 전체 허용 코드 목록은 이후 확정한다. 확정 전에는 `^F[1-9][0-9]*$` 형식만 검증하고 코드 자체를 표시한다.
- 항목마다 비용은 필수이며 정수 0 이상이다. 무료 정비는 0을 명시적으로 입력한다. 빈 값을 0으로 자동 처리하지 않는다.
- 총비용 `cost_krw`는 항목 비용을 더한 값이다. 클라이언트 값을 그대로 신뢰하지 않고 DB 트리거 등에서 계산·검증한다.
- JSON도 배열 여부, 최소 1개 항목, 필수 키, 코드 형식, 숫자 타입·정수·범위를 DB에서 검증한다.
- 구매일·연식·정비 당시 계기판 값은 선택 입력이다.
- 다음 점검은 정비일에서 달력 기준 6개월 뒤로 계산한다. 180일과 구분하며 대상 월에 같은 일자가 없으면 그 달 말일로 처리한다.
- 이 6개월은 앱의 사용자 지정 기본 규칙이며 제조사 권장 주기가 아니다.
- 주행거리 기반 다음 점검 컬럼은 현재 범위에서 제외한다.
- 다음 점검은 바이크별·정비 코드별 가장 최근 실제 정비일에 6개월을 더해 표시한다. 별도 완료 버튼·완료 상태 컬럼은 만들지 않는다.
- 같은 코드의 새 정비가 등록되면 이전 예정일은 대표 일정에서 제외된다. 다른 코드의 일정에는 영향을 주지 않는다.
- JSON 항목을 코드별로 펼친 뒤 실제 `maintenance_date`의 최댓값을 구한다. 등록 시각이나 배열 순서로 최신을 판단하지 않는다.
- 같은 날짜의 동일 코드 기록은 같은 다음 점검일을 가지므로 알림은 하나로 표시한다. 한 방문 안에서도 같은 코드의 작업 행은 여러 개일 수 있으며 비용은 모든 행을 합산한다.
- 과거 기록 추가, 기록 수정·삭제 때도 원본 기록으로 재계산한다. 최신 기록을 삭제하면 이전 기록 기준 일정이 다시 나타난다.
- 이전 기록은 완료 처리를 위해 삭제·변경하지 않는다. 현재 날짜가 예정일에 도달했거나 지났으면 점검 대상으로 표시한다.
- 여러 항목의 정비일은 방문 날짜 하나를 공유한다. 정비 코드의 의미를 바꾸거나 재사용하지 않는다.

### 정비 항목 저장 예시

코드와 작업명 조합은 구조 설명용이며 최종 코드 의미를 확정하는 예시는 아니다.

```json
[
  {"type_code": "F1", "name": "정비 항목 A", "cost_krw": 45000, "notes": ""},
  {"type_code": "F2", "name": "정비 항목 B", "cost_krw": 0, "notes": "무료 작업"}
]
```

위 예시의 방문 총비용은 45,000원이다.

## 6. 관계·접근 권한

### 본인 바이크에만 기록 연결

`user_id`와 `bike_id`를 각각 외래키로 설정하는 것만으로는 기록 소유자와 바이크 소유자가 같다는 보장이 없다.

권장 구현 방향:

1. `bikes`에 `(id, user_id)` 복합 UNIQUE 제약을 추가한다.
2. 두 로그 테이블의 `(bike_id, user_id)`가 `bikes(id, user_id)`를 참조하도록 복합 외래키를 설정한다.
3. 세 테이블 모두 RLS를 활성화한다.
4. 조회·삭제에는 `auth.uid() = user_id` 조건을 적용한다.
5. 추가·수정에도 `WITH CHECK`로 소유자 조건을 확인한다.
6. 사용자 변경·다른 사용자 바이크 연결을 화면 검증에만 맡기지 않는다.

- `user_id`를 `auth.uid()` 기본값으로 설정해도 RLS 검증은 필요하다.
- 비로그인 사용자는 실제 사용자 데이터를 조회·수정할 수 없게 한다.
- 테이블 권한은 필요한 작업에만 부여한다.
- Secret/service_role 키로 프런트엔드 접근을 구현하지 않는다.
- 계정 삭제 요청도 실제 Auth 사용자 삭제가 아니라 계정 아카이브로 처리한다. 세부 구현은 아래 계정 아카이브 절을 따른다.
- 바이크 삭제 요청은 항상 `archived` 상태 변경으로 처리한다. 사용자에게 실제 DELETE 권한을 부여하지 않고 외래키 `RESTRICT`를 유지한다.
- 보관과 새 로그 등록·바이크 변경 시 DB에서 같은 바이크 행을 잠그고 상태를 확인해 동시 요청에서도 보관 바이크에 로그가 추가되지 않게 한다. 함수·트리거는 인증과 소유권을 검증한다.
- 보관 바이크는 기존 기록 조회와 바이크 복원만 허용한다. 새 로그 등록, 기존 로그 수정·삭제, 바이크 정보·사진 변경은 복원 후 수행한다. 이는 “조회·복원만 가능” 기준을 적용한 것이다.
- RLS·트리거 등 DB에서도 이를 강제한다. 다른 active 바이크의 로그를 archived 바이크로 옮기는 수정도 거부한다.

## 7. 사진 저장 방향

- 바이크 대표 사진 1장은 제출 버전에 포함한다. 기본 CRUD 완료 후 업로드 기능을 연결한다.
- 예시 버킷 이름: `bike-photos`.
- 예시 파일 경로: `{user_id}/{bike_id}/{고유파일명}.jpg`.
- 비공개 버킷과 소유자 기반 Storage 정책을 권장한다.
- DB에는 버킷 내부 경로인 `photo_path`만 저장한다. 버킷 이름은 앱 설정에서 관리한다.
- 파일 형식·최대 용량·업로드 전 리사이즈 기준은 사진 구현 단계에서 확정한다.
- 바이크·계정 아카이브 시 사진 원본과 연결 경로를 유지한다.
- 활성 바이크의 사진 교체는 새 파일 업로드 → DB 경로 변경 순서로 처리한다. 보존 정책에 맞춰 이전 사진도 자동 삭제하지 않으며, 첫 버전에는 과거 사진 목록·복원 UI를 제공하지 않는다.
- DB 저장 실패 시 미연결 신규 파일이 남을 수 있으므로 경로를 추적하고 재시도·정리 대상을 구분한다. 아카이브된 연결 사진을 자동 정리 대상으로 취급하지 않는다. DB와 Storage 변경은 하나의 트랜잭션으로 자동 묶이지 않는다.
- Storage에도 계정 활성 상태·소유권·바이크 상태를 반영한다. 보관 바이크는 조회만 허용하고 업로드·교체·삭제는 차단한다. 만료된 서명 URL은 다시 발급한다.

## 8. 인덱스와 자동 처리

| 대상 | 권장 인덱스·처리 | 목적 |
| --- | --- | --- |
| `bikes` | `user_id` | 내 바이크 조회 |
| `bikes` | UNIQUE `(id, user_id)` | 소유권 포함 복합 외래키의 참조 대상 |
| `riding_logs` | `(user_id, bike_id, ride_date DESC)` | 바이크별 최신 라이딩 조회 |
| `maintenance_logs` | `(user_id, bike_id, maintenance_date DESC)` | 바이크별 최신 정비 조회 |
| 세 테이블 | `updated_at` 갱신 트리거 | 수정 시각 자동 기록 |

- 기본키·UNIQUE 제약이 만드는 인덱스를 중복 생성하지 않는다.
- 사용자 삭제 등 참조 정리 시 로그의 `user_id` 선두 인덱스도 활용할 수 있다.
- 검색 전용 인덱스는 데이터 규모와 실제 조회 조건을 확인한 뒤 추가한다.
- `updated_at DEFAULT now()`만 설정하면 수정 때 자동으로 바뀌지 않는다. 트리거 등 별도 처리가 필요하다.

## 9. 대시보드 집계 기준

| 표시값 | 데이터·기준 |
| --- | --- |
| 현재 계기판 주행거리 | `bikes.current_odometer_km` 및 확인 시점 |
| 이번 달 라이딩 횟수 | 선택한 바이크의 이번 달 `ride_date` 행 수 |
| 이번 달 라이딩 거리 | 같은 조건의 `distance_km` 합계 |
| 이번 달 정비 비용 | 이번 달 `maintenance_date` 기준 `cost_krw` 합계 |
| 최근 라이딩·정비 | 실제 라이딩일·정비일 내림차순 |
| 다음 점검 | 바이크·정비 코드별 최신 실제 정비일 + 6개월 |

- 집계는 로그인한 사용자와 선택한 바이크 범위에서 수행한다.
- 월 기준은 한국 현지 달력이다. 등록 시각인 `created_at`으로 과거 기록을 분류하지 않는다.
- 정비 총비용은 항목별 필수 비용의 합계다. 방문 총비용과 항목별 비용을 함께 더해 중복 집계하지 않는다.
- 전체 로그를 일부만 불러온 경우 그 목록만 더해 전체 합계로 표시하지 않는다.

## 10. 날짜·문자열·숫자 검증

| 항목 | 확정 기준 |
| --- | --- |
| 구매일·라이딩일·정비일 | 한국 기준 오늘 이하. 과거 날짜 허용 |
| 출발·도착 시각 | 둘 다 입력하거나 둘 다 생략. 출발 < 도착, 미래 시각 불가 |
| 라이딩 날짜와 시각 | 출발 시각의 한국 날짜와 ride_date 일치 |
| 다음 점검일 | 정비일 + 달력 6개월. 미래 날짜 허용 |
| 제조사·모델·별명 | 최대 50자 |
| 라이딩·정비 제목 및 항목별 작업명 | 최대 100자 |
| 출발지·각 경유지·도착지·정비소 | 각각 최대 100자 |
| 메모·항목별 메모 | 각각 최대 2,000자 |
| 필수 문자열 | 앞뒤 공백 제거 후 1자 이상 |
| 선택 문자열 | 비어 있으면 NULL. JSON 선택 메모는 생략 또는 빈 문자열 허용 |
| 거리 | integer, 소수 불가. 라이딩 거리는 1 이상, 계기판 값은 0 이상 |
| 항목별 비용 | 필수 integer, 0 이상. 소수·음수·누락 거부 |
| 금액 범위 | 각 금액과 방문 합계 모두 integer 범위(최대 2,147,483,647원) 이내 |

- 길이는 DB `char_length` 기준으로 검증한다. 브라우저 검증도 일치하도록 구현하고 이모지 등의 길이 차이를 고려한다.
- 날짜의 “오늘”은 DB 세션 시간대에 맡기지 않고 Asia/Seoul 기준으로 계산한다.
- 미래 여부처럼 현재 시각에 의존하는 검증은 INSERT/UPDATE 시 트리거로 처리하고, 고정 길이·범위·필수값은 CHECK/NOT NULL 등으로 검증한다.
- 화면에서만 검증하지 않는다. 다만 정수 컬럼은 입력 변환 과정에서 소수가 반올림될 수 있으므로 API/RPC 입력에서도 원래 숫자를 검증하도록 구현안을 제시한다. 단순 정수 캐스팅으로 검증을 대체하지 않는다.
- 실제 계기판 값은 늦게 입력한 과거 기록보다 작을 수 있으므로 기록 등록만으로 current_odometer_km을 갱신하거나 과거 데이터를 임의 수정하지 않는다.

## 11. 계정 아카이브

- UI에서는 실제 탈퇴·영구 삭제가 아니라 **계정 비활성화(데이터 보관)**임을 명확히 설명한다.
- Auth 사용자·바이크·라이딩·정비·사진은 보존한다. Auth 사용자를 deleteUser로 삭제하지 않는다.
- 계정 아카이브는 바이크 status만 바꾸는 것으로 대체할 수 없다. 새 로그인·기존 세션의 데이터 접근까지 차단해야 한다.
- 서비스 데이터 테이블 3개를 유지하는 방향으로, Auth의 관리자 전용 app_metadata에 계정 상태 `account_status`를 관리하는 구현안을 우선 사용한다. 활성 상태는 active, 보관 상태는 archived로 한다. 신규·기존 사용자 기본 활성 처리도 명시한다.
- 사용자 수정 가능한 user_metadata를 권한 근거로 사용하지 않는다.
- Auth 관리자 API 호출은 브라우저에서 하지 않는다. 계정 아카이브만 Supabase Edge Function 등 신뢰할 수 있는 서버 측 처리가 필요하다. 별도 Node.js 서버는 만들지 않는다.
- 서버 측에서 요청 사용자의 인증을 검증하고, 요청 본인만 비활성화한다. 대상 사용자 ID를 클라이언트가 자유롭게 지정하게 하지 않는다.
- 관리자 전용 상태 갱신과 로그인 차단을 수행하고, 프런트엔드는 성공 응답 후 세션·개인 데이터를 비운다. 중간 실패 시 성공으로 표시하지 않고 재시도 가능하게 한다.
- 로그인 차단만으로 기존 액세스 토큰의 DB 접근이 즉시 끝난다고 가정하지 않는다. DB·Storage 접근에서도 현재 계정 상태를 확인한다.
- JWT app_metadata는 토큰 갱신 전까지 이전 값일 수 있다. 즉시 차단을 위해 DB 보안 함수 등에서 서버가 관리하는 현재 상태를 조회하는 방식을 설계한다. auth 스키마 전체 읽기 권한을 브라우저에 부여하지 않는다.
- 보안 함수는 최소 권한, 고정 search_path, 안전한 스키마 명시, 호출자 본인 상태만 반환하는 조건으로 구현한다. RLS 재귀도 피한다.
- 이미 발급된 사진 서명 URL은 만료 전까지 유효할 수 있다. 짧은 유효기간을 사용하고 그 한계를 문서화한다.
- 계정 복원은 첫 버전에서 관리자 수동 처리로 한다. 계정 아카이브 시 각 바이크 status는 그대로 보존해 복원 시 이전 상태를 유지한다.
- Edge Function 설정·배포 방법과 필요한 비밀값은 별도 안내한다. 해당 설정 전에는 계정 아카이브 버튼을 동작 완료로 가장하지 않는다. 다른 기본 기능 구현은 계속 진행할 수 있다.

## 12. 확정 사항과 구현 시 선택할 항목

### 확정 사항

- 사진 선택, 거리 정수, 라이딩 거리 0 불가.
- 제조사·모델 자유 입력. 구매일·연식·정비 당시 계기판 값 선택.
- 라이딩 R 계열·정비 F 계열 코드 사용, 이름은 이후 확정.
- 한 정비 방문에 여러 작업·비용 입력. JSON 배열 저장, 방문 총비용은 DB 계산.
- 다음 점검은 바이크·정비 코드별 최신 실제 정비일 + 6개월. 새 동일 코드 정비가 이전 일정을 대체.
- 첫 화면 생성 후 여러 바이크 선택 UI 구현.
- 바이크·계정 삭제 요청은 아카이브, 데이터·사진 보존.
- 보관 바이크는 조회·복원만 가능, 새 로그 등록 불가.
- 날짜·문자열 제한은 10절 적용.

### 명시적 미정 사항

- 라이딩·정비 코드별 한국어 이름과 최종 허용 목록. 확정 전에는 코드만 표시한다.
- 사진 형식·최대 용량·리사이즈 규격. 사진 단계에서 변경 가능한 설정값으로 권장안을 제시한다.
- 최종 색상·폰트. 밝은 반응형 화면 기준으로 제안한다.

보완 구현 기준: 한 정비 방문 내 중복 코드는 허용하되 점검 일정은 코드당 하나로 집계한다. 사진 교체 후 이전 파일도 자동 삭제하지 않는다. 계정 복원은 관리자 처리다.

## 13. 구현 순서와 Codex에 전달할 요청

1. 이 문서의 요구사항·테이블 관계·권한·화면 구조를 검토한다.

### 최종 확인 기준

- [ ] 사용자 A가 B의 바이크·로그·사진을 조회·수정할 수 없다.
- [ ] A의 로그를 B의 바이크에 연결할 수 없다.
- [ ] 소수 거리, 0km 라이딩, 음수·누락 비용, 미래 기록일, 초과 길이가 거부된다.
- [ ] 0원 정비가 저장되고 항목 합계·방문 합계가 일치한다.
- [ ] 다중 정비 항목에서 코드별 최신 점검일이 정확하며 과거 기록 등록 순서에 영향받지 않는다.
- [ ] 최신 정비 수정·삭제 후 점검일이 재계산된다.
- [ ] 자정 넘는 라이딩, 한국 월 경계, 월말 + 6개월 계산이 정확하다.
- [ ] 보관과 새 로그 등록 동시 요청에서도 보관 바이크에 새 로그가 생기지 않는다.
- [ ] 바이크 보관은 사진·기록을 보존하며 복원 후 사용 가능하다.
- [ ] 계정 아카이브 후 기존 세션으로도 새 DB·Storage 접근이 차단된다. 기존 서명 URL 만료 한계는 문서화한다.
- [ ] 계정 전환 시 이전 사용자의 데이터나 늦은 요청 결과가 노출되지 않는다.
- [ ] 페이지 일부 데이터만 합산한 값이 전체 통계로 표시되지 않는다.
- [ ] PC·모바일 및 GitHub Pages 하위 경로에서 실행된다.
